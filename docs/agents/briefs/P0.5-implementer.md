## Requirements

1. P0.5-R1 Stiff damped string with an energy-conserving finite-difference scheme and configurable grid.
2. P0.5-R2 Hammer contact with an iterative (Newton) energy-conserving scheme, deliberately different from the engine's SAV method.
3. P0.5-R3 Bridge as a lumped mass–spring–dashpot or a conductance, shared by several strings, with both polarisations.
4. P0.5-R4 Finite-difference orthotropic Kirchhoff plate on a rectangle, coupled to strings at bridge points.
5. P0.5-R5 Distributed string–barrier collision (penalty potential, Newton solve).
6. P0.5-R6 Tension modulation and longitudinal waves (iterative scheme).
7. P0.5-R7 Grid-refinement and energy-monitor tools; Python bindings and a CLI that render scenarios to features and WAV.

### Independence rules (the reason this phase exists)

- Targets under `reference/` and `tools/reference-cli/` may use: the include directory `engine/include` for description structs (header-only use), `pme_analysis`, `nlohmann_json`, the standard library. They MUST NOT link any `pme_<module>` library, `pme_engine`, or include anything under `engine/src/`. Add a configure-time check (as P0.3 did for engine isolation, `cmake_language(DEFER …)`) that fails if any reference target's link closure contains `pme_engine` or a `pme_<module>` target; show in your report that it fires in a scratch build.
- Use physical-space finite differences (and Newton iterations for nonlinearities), not modal synthesis: no oscillator coefficients of SPEC-OSC, no SAV, no modal shape tables. All arithmetic in float64. Every function implementing a formula cites the SPEC section it reproduces and the scheme's source (for example Bilbao, *Numerical Sound Synthesis*, 2009, chapter and equation) in a comment.
- Namespace `pme::ref` (or `pme_ref`); headers under `reference/include/pme/ref/`.

### How to meet each requirement

**P0.5-R1 — string.** A stiff string per SPEC-STR (ρA, T, EI from `StringParams` with SPEC-STR's wound-string and tension-for-pitch formulas re-implemented here, not called from the engine), simply supported ends (y = ∂²ₓy = 0) and optionally clamped ends, on a uniform grid of N intervals with Δt from the scenario's fs times an integer oversampling factor. Use an energy-conserving scheme with a discrete energy identity, for example the implicit θ-scheme for the stiff string (Bilbao 2009, §7.1–7.2) with banded direct solves. Losses: frequency-dependent loss of the form 2σ₀∂ₜy − 2σ₁∂ₜ∂²ₓy (+ optional 2σ₃∂ₜ∂⁴ₓy), with σ₀ = b₁, σ₁ = b₃T/ρA, σ₃ = b₃EI/ρA so that the continuous decay is σ(ω) = b₁ + b₃ω² (SPEC-STR "Losses"). **b₂√ω has no local finite-difference form: the reference accepts only b₂ = 0 and rejects other values with a clear error.** State this in docs/dev/reference-solver.md: comparisons against the engine (A2-T3 and later) use b₂ = 0. Outputs: displacement and velocity at observation points, the force at x = L for the bridge, discrete energy and the loss term per step.

**P0.5-R2 — hammer.** A lumped hammer (mass m\_H, felt law K[δ]₊^p per SPEC-HAM, Hunt–Crossley term optional) contacting the string over a window (point or raised cosine of width b), solved each step with Newton's method on a discrete-gradient (energy-conserving) form of the potential, converged to a residual of 10⁻¹⁴ relative or 50 iterations (report non-convergence as an error, never silently). Also a "rigid wall" mode (hammer against a fixed felt contact) for P0.5-T3. Energy: kinetic + felt potential + string energy conserved without Hunt–Crossley losses.

**P0.5-R3 — bridge.** A bridge point shared by several strings, two polarisations each: (a) lumped mass–spring–dashpot, and (b) pure conductance G (force-to-velocity, SPEC-BRG). Strings couple at x = L through the bridge displacement as the boundary condition, solved jointly per step so the coupled system keeps an energy balance (dashpot and conductance terms dissipative, everything else conserved). Unit tests `P0.5-R3 …`: lossless lumped bridge conserves total energy to 10⁻¹² relative per step; a flexible (EI = 0) string on a pure conductance decays at σ = −f₀ ln[(1 − Z₀G)/(1 + Z₀G)] within 1% on a fine grid (the ORC-06 formula; a cross-check of the reference, not the engine's oracle).

**P0.5-R4 — plate.** Orthotropic Kirchhoff plate on a rectangle L\_x × L\_y, uniform thickness, grain along x (θ\_g = 0), with D₁₁, D₂₂, D₁₂, D₆₆ from SPEC-BODY, simply supported edges (clamped and free MAY be added), on a uniform grid; energy-conserving explicit or implicit scheme (Bilbao 2009, chapter 12 for the isotropic case; extend to the orthotropic operator). Accept `PlateParams` and reject features the reference does not model (polygon outline, thickness grid, ribs, bridges as beams, rim stiffness) with a clear error naming the field. Strings attach at bridge points (positions in the body frame, `Point`); the string's end force drives the plate locally (bilinear spreading and the matching interpolation for the plate displacement, so coupling is energy-neutral).

**P0.5-R5 — barrier.** A distributed barrier along the string, b(x) sampled on the string grid, penalty potential K[b − y]₊^α (or the side convention of SPEC-PLK) with optional contact damping, solved by Newton on the discrete-gradient form at every grid point in contact. Unit tests `P0.5-R5 …`: a string released onto a flat barrier keeps total energy constant to 10⁻⁹ relative per step without contact damping and non-increasing with it (the ORC-15 setup, run on the reference).

**P0.5-R6 — geometric nonlinearity.** Tension modulation (Kirchhoff–Carrier) and coupled longitudinal–transverse motion per SPEC-GEO, each with an iterative energy-conserving scheme (for example Bilbao 2009 §8.1–8.2). Unit tests `P0.5-R6 …`: lossless energy conservation to 10⁻¹¹ relative per step for a large-amplitude pluck; pitch glide direction and the longitudinal mode frequencies match SPEC-GEO's linear values at small amplitude within 0.1%.

**P0.5-R7 — tools.**

- **Scenarios**: a JSON scenario format (documented, with a JSON Schema at `reference/scenario.schema.json`, `schema_version: 1`) naming strings (the `StringParams` fields), hammer, bridge, plate, barriers, geometric nonlinearity switches, excitation (initial displacement, hammer velocity), observation points, fs, oversampling, grid sizes and duration. Read with nlohmann/json.
- **CLI** `tools/reference-cli` (executable `pme_reference_cli`): `render <scenario.json> --features <out.json> --wav <out.wav> [--energy <out.json>]` writes golden-feature JSON (through `pme_analysis`'s writer, so the comparator reads it), a float WAV of the observation signals, and an energy trace; `refine <scenario.json> --grids N1,N2,N3 --quantity partial-frequencies` reports observed convergence orders.
- **Energy monitor**: per step total energy, its components and the loss term; summary through `pme_analysis` energy accounting.
- **Python bindings** (nanobind, module `pme_reference`, sources in `reference/python/`): `render(scenario: dict | str) -> dict` returning NumPy arrays for observation signals and energy, plus the features dict. Add a mypy override for `pme_reference` in `pyproject.toml` (`ignore_missing_imports`), or generate a stub; regenerate `uv.lock` only if dependencies change.
- `reference/README.md`: build, run, scenario format, limits (b₂ = 0; rectangle plates only).

- **P0.5-T2** lossless energy is conserved to 10⁻¹² relative per step;

### How each test is built

All are doctest `TEST_CASE`s named `P0.5-Tn …` in `reference/tests/`, labels `integration` (and `unit` for small ones). **Runtime:** each test case must finish within 60 s in `linux-debug` on a CI runner. Cases that need fine grids to meet a card tolerance are registered only for optimised builds (`CMAKE_BUILD_TYPE` Release or RelWithDebInfo), so they still run in CI on all three systems through the `*-rt-safety` presets and macos-universal's release build. State in docs/dev/reference-solver.md which cases run where.

**P0.5-T1.** Lossless, simply supported stiff string (pick L = 1 m, f₁ = 110 Hz, B ≈ 10⁻⁴ and a second case with B ≈ 10⁻² so stiffness matters). Analytic: ω\_n² = (T k\_n² + EI k\_n⁴)/ρA, k\_n = nπ/L (SPEC-STR "Modes"). For at least three refinements (N doubling, Δt refined so the scheme's stability and accuracy hold), measure the first five partial frequencies from the simulated output with `pme_analysis` partial tracking (and, if you like, from the scheme's exact discrete dispersion relation as a cross-check). Pass: the observed order from the two finest grids is within 10% of the scheme's theoretical order (state it, normally 2), for every one of the five partials, and the error decreases monotonically.

**P0.5-T2.** Lossless string (and, in separate cases, lossless string + lumped bridge, string + hammer without Hunt–Crossley, string + barrier without damping, string with tension modulation): max over n of |Hⁿ⁺¹ − Hⁿ| / |H⁰| ≤ 10⁻¹² for the linear cases. For Newton-solved cases the bound is the same if the iteration converges to round-off; if it cannot, report the achieved value and stop (do not loosen).

**P0.5-T3.** Rigid wall: m = 8 g, v = 3 m/s, p = 2.5 (the ORC-08 setup), K from SPEC-HAM's typical range (state it; test at least two K values). Analytic contact time from SPEC-HAM "Oracle": t\_c = 2(δ\_m/v)·√π Γ(1 + 1/(p+1)) / Γ(½ + 1/(p+1)), δ\_m = ((p+1) m v² / (2K))^(1/(p+1)). Measure t\_c with `pme_analysis` contact-time measurement (sub-sample) at a fine time step. Pass: |t̂\_c / t\_c − 1| ≤ 0.001; rebound speed −v within 10⁻⁹ relative (energy conserving).

**P0.5-T4.** Simply supported orthotropic rectangle (spruce-like E\_L, E\_R, G\_LR, ν\_LR, ρ, h; state values), analytic ω\_mn² = [D₁₁(mπ/L\_x)⁴ + 2(D₁₂ + 2D₆₆)(mπ/L\_x)²(nπ/L\_y)² + D₂₂(nπ/L\_y)⁴] / (ρh). Compare the lowest ten modes, measured from the simulated response at a generic point with `pme_analysis` (or from the discrete operator's eigenvalues, with at least the lowest three also measured from simulation). Pass: every one within 0.1%.

**Python** (`tools/tests/test_p0_5_r7_*.py`): import `pme_reference` from `PME_REFERENCE_PYDIR` (skip when unset), render a small scenario, check the arrays' shapes and that the features file matches the CLI's output for the same scenario exactly. Docstrings begin with the ID.
