# Instrument file format (B1)

SPEC sections implemented: SPEC-INST "Instrument definitions" (the instrument table, "Piano defaults",
"Instrument file") and SPEC-API "Engine interfaces" ("Descriptions", "Event addressing", "Parameter
classes"). Field meanings and units come from SPEC-STR "Stiff string model", SPEC-HAM "Hammer and
action", SPEC-DMP "Dampers and pedals", SPEC-PLK "Plucked exciters and barriers", SPEC-BODY
"Soundboard and bodies" and SPEC-BRG "Bridge coupling", through the frozen description headers
(`engine/include/pme/*.hpp`, interfaces-v2 = 300b995). Segment order follows SI-0010 as decided by the
orchestrator (see "Cross-field rules").

An instrument is data, not code (SPEC-INST). One instrument is one UTF-8 JSON document with a schema
version, plus an optional manifest of binary blobs referenced by hash. This note describes the
format, the two loaders and how to extend them.

| What | Where |
| --- | --- |
| JSON Schema (draft 2020-12) | `compiler/pme_compiler/schema/instrument.schema.json` |
| Field table (single source of truth) | `compiler/pme_compiler/schema/fields.py` |
| Generator (schema, Python models, C++ reader/writer) | `python -m pme_compiler.schema.generate [--check]` |
| Python models, loader, writer, migration | `compiler/pme_compiler/schema/` (`models.py`, `loader.py`, `validate.py`, `migrate.py`, `canonical.py`) |
| C++ loader (non-real-time) | `engine/src/runtime/loader/`, target `pme_loader`, header `pme/loader/instrument_file.hpp` |
| Example instruments | `instruments/examples/<name>/instrument.json`, generators in `compiler/pme_compiler/examples/` |
| Shared test fixtures | `compiler/tests/data/b1/` (regenerated by `gen_fixtures.py`) |

The loader is not an engine module. It is never linked into `pme_engine` or a `pme_<module>` target and
nothing in it is reachable from `Engine::process`; the engine-side code that will consume an
`InstrumentDesc` (C1, `compileInstrument`) receives the description from the application.

## Format rules

- Top level: `"format": "pme-instrument"`, `"schemaVersion": 1`, `"instrument": {...}` (the
  `InstrumentDesc`), `"blobs": [...]` (the manifest; optional, absent means empty).
- Field names are the C++ member names exactly (`dCore`, `rhoCore`, `ECore`, `f1Target`, `kappaL`,
  `unisonDetuneCents`, ...), nested as the structs nest. Enums are their enumerator names as strings
  (`"Pinned"`, `"At0"`, `"HuntCrossley"`, `"PlateModel"`, ...).
- `ExciterParams` is an object with exactly one key naming the alternative: `hammer`, `pluckPulse`,
  `plectrum`, `finger`, `initialDisplacement`. The `std::optional` members `NoteGroupDesc::exciter` and
  `SegmentDesc::damper` are omitted when empty. `Point` is `{"x": ..., "y": ..., "z": ...}`.
- A member whose header declares a default member initialiser with a value (`longitudinalModes{8}`,
  `kappaL{0.026}`, `TuningCurve::referencePitch{440.0}`, the `Defaults`, `UnaCordaParams` and
  `DamperParams` timing defaults, `strengthGamma{1.0}`, `boundary{Pinned}`, ...) is optional and takes
  the header's value when absent. A struct member whose struct has only such members (`unaCorda`,
  `defaults`) is optional as a whole. Every other member is required, including empty vectors
  (`sigmaOverride`, `barriers`, `stretchCents`, ...) which are written as `[]`.
- Unknown keys are errors (`"additionalProperties": false`).
- Integers may be written `5` or `5.0`; booleans, strings and arrays are never coerced.
- Numbers must be finite. NaN, Infinity, numbers out of float64 range, a byte order mark, an unpaired
  surrogate escape and invalid UTF-8 are parse errors in both loaders. Nesting deeper than 64 levels is a
  `structure` error (a real file nests about 12).
- Integer members are C++ `int` and are bounded to 32 bits (`-2147483648 ... 2147483647`) in the schema;
  manifest integers (`offset`, `shape`) are bounded to 2^53 - 1 so that every JSON tool reads them
  exactly.
- `BodyParams::modalTableHash` is the manifest hash string `"sha256:<64 lower-case hex>"`. It must name an
  entry of `blobs` when `source` is not `PlateModel` and be empty when it is. For a non-`PlateModel`
  source the `plate` object is still required (it holds the C++ default, all zeros, which the
  member bounds allow; see the plate rule below).

### Canonical form

Both writers (`pme_compiler.schema.dumps`, `pme::loader::writeInstrument`) produce byte-identical text:

- 2-space indentation, `"key": value`, one array element per line, `[]` and `{}` for empty containers,
  LF line ends, one final newline, UTF-8 without escaping non-ASCII characters (control characters,
  `"` and `\` are escaped as JSON requires).
- Object keys in the schema `properties` order, which is the C++ member declaration order.
- Every member is written, defaults included; only an empty `std::optional` is omitted.
- Numbers: `int` members as integers; `double` members as the shortest decimal that round-trips to the
  same float64, laid out like nlohmann/json lays out numbers: fixed notation with at least one decimal
  (`100.0`, `0.0001`, `123456.789`) when the decimal exponent is between -4 and 15, otherwise
  `d[.ddd]e[+-]XX` with at least two exponent digits (`1e-05`, `2e-09`, `1.5e+300`, `1e+15`). Python's
  `repr(float)` differs from nlohmann's layout in the range 1e15 to 1e16 and in no other case, so the
  Python writer takes the shortest digits from `repr` and applies the nlohmann layout; the C++ writer
  takes them from `std::to_chars` (shortest round trip) and applies the same layout. Negative zero is
  `-0.0`.

## Errors

Every error carries `path` (a JSON Pointer, RFC 6901; `~` is `~0`, `/` is `~1`; empty for the document
root), `code` from the closed list below, and a human-readable `message` that names the expected value.
Both loaders report the same set of (path, code) pairs for the same input; messages may differ.

| Code | Meaning |
| --- | --- |
| `parse` | Not valid JSON (or BOM, invalid UTF-8, lone surrogate, non-finite number, unreadable file). Path is the root. |
| `type` | A value of the wrong JSON type, or a string that does not match its pattern (a hash). A `type` error hides every other error at the same path. |
| `missing` | A required member is absent. Path is the missing member. |
| `unknown_key` | A member the schema does not define. Path is the member. |
| `range` | A number outside its bound (see the member tables). |
| `enum` | A value outside its enumeration (enumerator name, `side`, `format`, blob `dtype`). |
| `version` | `schemaVersion` is not an integer or is above the current version (or negative). |
| `migration` | A file of an older version lacks data that has no source in that version. |
| `reference` | A cross-reference does not resolve (`bridgePoint`, `modalTableHash`). |
| `duplicate` | A key, blob path, blob hash or array name appears twice. |
| `structure` | Array or object size or arrangement is wrong (minimum items, exactly-one exciter key, grid size, nesting depth, segment order). |
| `blob` | A manifest or blob-file inconsistency (path form, alignment, overlap, offset past the end, wrong hash, missing file). |

Rules common to both loaders:

- All errors found are reported, sorted by (path, code), one per pair, at most 100.
- Validation runs in phases and stops after the first phase that reports an error: (1) text and
  parse, (2) schema version, (3) migration (older versions only), (4) structure: types, bounds,
  required and unknown members, (5) cross-field rules and manifest consistency, (6) blob files
  (only when a file path is loaded). A file with one structural error and one cross-field error therefore
  reports only the structural error: cross-field rules need a structurally valid document.
- `loadInstrument(text)` / `loads(text)` never touch the file system and so skip phase 6.
- On failure the C++ `out` parameter is unchanged and the function returns `Status::InvalidArgument`;
  no exception crosses the API (exceptions from nlohmann/json are not enabled for parsing and every
  entry point catches the rest).

## Cross-field rules

JSON Schema cannot express these; both loaders check them after the schema, with these paths and codes.

| Rule | Code | Path |
| --- | --- | --- |
| `key` unique among groups with `key >= 0` (SPEC-API "Event addressing", SI-0004) | `duplicate` | `/instrument/groups/<g>/key` of the later group |
| Every `bridgePoint` < size of `bridgePoints` | `reference` | `.../segments/<s>/bridgePoint` |
| `dOuter >= dCore` (SPEC-STR "Wound strings") | `range` | `.../segments/<s>/string/dOuter` |
| `BarrierParams` arrays `x`, `b`, `w` of equal length | `structure` | `.../segments/<s>/barriers/<k>` |
| **Segment order (SI-0010):** a group's first segment has `bridgeEnd` `AtL` | `structure` | `.../segments/0/string/bridgeEnd` |
| `thicknessGrid` non-empty: `thicknessNx >= 2`, `thicknessNy >= 2` | `range` | `/instrument/body/plate/thicknessNx` and `thicknessNy` |
| `thicknessGrid` size = `thicknessNx * thicknessNy` | `structure` | `/instrument/body/plate/thicknessGrid` |
| `outline` has 0 vertices (rectangle) or at least 3 | `structure` | `/instrument/body/plate/outline` |
| Source `PlateModel`: `youngsL`, `youngsR`, `shearLR`, `density`, `fMax` > 0; `thickness` > 0 if the grid is empty; `lengthX`, `lengthY` > 0 if the outline is empty | `range` | `/instrument/body/plate/<member>` |
| Source `PlateModel`: `modalTableHash` empty | `structure` | `/instrument/body/modalTableHash` |
| Source not `PlateModel`: `modalTableHash` equals the hash of a `blobs` entry | `reference` | `/instrument/body/modalTableHash` |
| Manifest consistency (see "Blob manifest") | `blob`, `duplicate` | `/blobs/...` |

**SI-0010 (segment order).** SI-0010 is open in the spec-issue log; the orchestrator decided item 1 by
default: the SI-0004 tuning rule applies to speaking (`AtL`) segments only, and a rear or duplex
(`At0`) segment takes the tension of the speaking segment just before it in the group's `segments`
order. The loaders enforce the consequence as one separately named check (`checkSegmentOrder` in
`checks.cpp`, `_check_segment_order` in `validate.py`): the first segment of a group must be `AtL`, so
every `At0` segment follows a speaking segment. If SI-0010 item 1 is rejected, delete these two
functions, their call sites, the `rear-segment-first` fixture, the line in `expected.json` and this
paragraph. SI-0010 item 2 (`sigma_felt`) adds no member in this version; rear segments carry only
`muteRatio`. The generic-grand-88 example has no rear segments.

The plate positivity rule exists because `PlateParams` must be representable for the other sources
(a `ModalTable` body ignores `plate`), so the member bounds are "at least 0"; the strict bound applies
only where the plate is used. The one-vertex and two-vertex outline rule is a reading of "polygon":
SPEC-BODY and SI-0003 do not state a minimum, so a degenerate outline is the only thing rejected.

## Versions and migrations

Current version: **1** = the interfaces-v2 structs documented in this note. A file with
`schemaVersion` above the current version, below 0, or not an integer is an error `version` and is not
migrated. Writers always write the current version. Loaders report the source version (`sourceVersion` in
C++, `source_version` in Python) and migrate older files on load.

Version history:

| Version | Structs mirrored | Status |
| --- | --- | --- |
| 0 | interfaces-v1 (2daee85) | Never shipped; exists so that the migration path is exercised from the first release |
| 1 | interfaces-v2 (300b995, ICR-0001) | Current |

Version 0 differs from version 1 as ICR-0001 describes: no `unisonDetuneCents` on segments;
`PluckPulse.peakForce` instead of `peakForceMax` and no `strengthGamma`; `Plectrum.driverSpeed` instead
of `driverSpeedMax` and no `position`, `angle`, `strengthGamma`; `Finger` with `mass`, `stiffness`,
`alpha`, `muFlesh`, `width`, `driverSpeed`, `slipHeight`; `PlateParams` without `outline`,
`thicknessNx`, `thicknessNy`, `thicknessGrid`, `bridges`, `rimRotationalStiffness`; no
`InitialDisplacement` exciter.

Migration 0 to 1 (`pme_compiler.schema.migrate`, `migrate.cpp`; identical steps, applied before
validation, so a migrated file is validated as version 1):

| Version 0 | Version 1 |
| --- | --- |
| no `unisonDetuneCents` | `unisonDetuneCents: 0` |
| `PluckPulse.peakForce` | `peakForceMax` (same value) and `strengthGamma: 1` |
| `Plectrum.driverSpeed`, no `position`/`angle` | error `migration` at the plectrum's path: no version 0 source for `position` and `angle`; supply them. If both are present the plectrum migrates (`driverSpeed` -> `driverSpeedMax`, `strengthGamma: 1`) |
| `Finger` with the version 0 members | error `migration` at the finger's path: no version 0 source for `driverStiffness`, `position`, `angle`. If all three are present it migrates (`mass` -> `tipMass`, `stiffness` -> `contactK`, `alpha` -> `contactAlpha`, `driverSpeed` -> `driverSpeedMax`, `strengthGamma: 1`) |
| `PlateParams` with the version 0 members | same values; the new members are empty or 0 (rectangle plate, uniform thickness, no beam bridges, no rotational rim stiffness) |

A key that is already present in its version 1 form is never overwritten (`peakForce` next to
`peakForceMax` leaves `peakForce` as an unknown key). When a migration reports errors, only those errors
are returned.

## Blob manifest

Binary data (the modal table of a `ModalTable` or `MeasuredMobilityFit` body, produced by B2/B3/E-phases)
is stored outside the document and listed in `blobs`. The manifest is not part of `InstrumentDesc`
(frozen); the C++ loader returns it beside it (`InstrumentFile::blobs`).

Each entry:

| Member | Meaning |
| --- | --- |
| `hash` | `"sha256:"` and 64 lower-case hex digits of the whole file |
| `path` | Relative to the instrument file's directory; forward slashes; no empty, `.` or `..` part; no leading `/`, no `\`, no `:` |
| `producer` | `{"tool": ..., "version": ...}`, the producing tool and its version |
| `arrays` | List of `{name, dtype, shape, unit, offset}`: `dtype` one of `float32`, `float64`, `int32`, `uint32`; `shape` a non-empty list of positive integers; `unit` as `x-unit`; `offset` in bytes from the start of the file, a multiple of the element size |

Blob files are raw little-endian arrays at the given offsets, row-major. Both loaders check, from the
manifest alone: path form (`blob`), a repeated path or hash (`duplicate`), a repeated array name inside
one entry (`duplicate`), alignment of each offset (`blob`), overlap of arrays inside one entry (`blob`,
at the later array's offset), and arrays larger than 2^53 bytes (`blob`). When the file is loaded from
disk they also check, for each blob file that exists, that every array ends within the file (`blob` at
the array's `offset`); and when `verifyBlobs` is true (the default of `try_load`/`load` in Python, false
for the C++ engine-side load) that each file exists and that its SHA-256 equals `hash` (`blob`). The hash
is computed by Python `hashlib` and by a small SHA-256 in `engine/src/runtime/loader/sha256.cpp`, tested
with the FIPS 180-4 example vectors.

## Unit vocabulary

Every numeric property (and every array of numbers) in the schema carries `"x-unit"`, one of:
`1` (dimensionless), `index` (integer index or count), `m`, `kg`, `kg/m^3`, `Pa`, `N`, `N/m`, `N/m^2`,
`N/m^p`, `N/m^alpha`, `N/m^(alpha+1)`, `Hz`, `1/s`, `s^(-1/2)`, `s`, `s/m`, `s/kg`, `kg/s`, `m/s`, `rad`,
`cent`, `bytes`. Units are SI. Coefficients "per unit moisture content" keep the unit of the quantity
(MC is dimensionless); `rimRotationalStiffness` (N m/rad per m) is recorded as `N`, since rad is
dimensionless.

## Members, units and constraints

Constraints are physical only, taken from SPEC or from the header comments of the frozen structs; none
is a "typical range". "Source" names the SPEC key the member's description in the schema cites.
Bounds on positive magnitudes (length, mass, density, modulus, stiffness, time constant, exponent) come
from their being physical magnitudes in the cited SPEC formula; bounds on dimensionless fractions
(`packing` in (0, 1], `muteRatio`, `strikeRatio`, `xRatio`, `s0`, `s1`, `rhoUpright`, the half-pedal
limits, `sympatheticGain` in [0, 1]) come from SPEC defining the quantity on that interval; `key` in
-1 to 127 is SPEC-API "Event addressing" with SI-0004; `side` in {-1, +1} is SPEC-PLK "Distributed
barriers"; `leavingString >= -1` is the SPEC-HAM table "String that leaves the hammer" ("None" is -1).
"32-bit int" means the C++ `int` range. Members that the header leaves unbounded (angles, detunes,
Poisson ratios, moisture slopes, positions) have no constraint.

## Loaders

### C++ (`engine/src/runtime/loader/`, namespace `pme::loader`, static library `pme_loader`)

```cpp
struct LoadError { std::string path; std::string code; std::string message; };
struct InstrumentFile { InstrumentDesc desc; std::vector<BlobEntry> blobs; int sourceVersion{}; };
Status loadInstrument(std::string_view json, InstrumentFile& out, std::vector<LoadError>& errors);
Status loadInstrumentFile(const std::filesystem::path&, bool verifyBlobs, InstrumentFile& out,
                          std::vector<LoadError>& errors);
Status writeInstrument(const InstrumentFile&, std::string& json);   // canonical form
```

`Ok`, or `InvalidArgument` with at least one `LoadError` and `out` unchanged (ADR-0006). The library
links `nlohmann_json::nlohmann_json` privately (ADR-0005) and includes `engine/include`. A configure-time
check in `engine/tests/loader/CMakeLists.txt` fails the configure step if any engine target reaches
`pme_loader`; the nlohmann check of `cmake/pme_testing.cmake` still applies. The reader and writer of
every description struct are generated into `fields_generated.hpp` (checked in; `generate.py --check`
fails when stale); hand-written code is the pipeline (`instrument_file.cpp`), the validating reader
(`reader.cpp`), migration (`migrate.cpp`), cross-field rules (`checks.cpp`) and the manifest
(`blobs.cpp`, `sha256.cpp`).

### Python (`pme_compiler.schema`)

```python
from pme_compiler.schema import load, loads, dumps, dump, validate, try_load, try_loads, migrate
file = load("instruments/examples/test-monochord/instrument.json")  # path (verifies blobs) or text
text = dumps(file)                    # canonical form
errors = validate(json.loads(text))   # [] if valid; LoadError(path, code, message) otherwise
```

`models.py` holds frozen keyword-only dataclasses with the C++ member names, types and defaults
(`models.InstrumentDesc`, `models.HammerParams`, ...; `ExciterParams(e=...)` holds one alternative,
enums are `Literal` strings); `models.InstrumentFile(desc, blobs, source_version)` is the whole file.
`load`/`loads` raise `InstrumentError` (with `.errors`) on an invalid document; `try_load`/`try_loads`
return `(file, errors)`. `validate(document)` runs the version check, migration, the schema
(`jsonschema.Draft202012Validator`), the cross-field rules and the manifest checks on a parsed
document, without reading blob files. Python maps schema keywords to codes as follows: `type` -> `type`,
`required` -> `missing`, `additionalProperties` -> `unknown_key`, `minimum`/`maximum`/`exclusive*` ->
`range`, `minItems`/`minProperties`/`maxProperties` -> `structure`, `enum` -> `enum`, `pattern` ->
`type`.

## Adding a field

1. Add the member to the frozen header (that needs an ICR; B1 changes no header).
2. Add it to `fields.py` in declaration order (unit, bound, default, SPEC key). Run
   `python -m pme_compiler.schema.generate`; this rewrites the schema, `models.py` and
   `fields_generated.hpp`. A struct that is new needs a `Struct` entry and, for the C++ side, the
   header include in `instrument_file.cpp` already covers `pme/instrument.hpp`.
3. If the member is new to a released version, bump `CURRENT_VERSION` (`fields.py`) and
   `kCurrentSchemaVersion` (`instrument_file.hpp`), and write the migration in both
   `pme_compiler/schema/migrate.py` and `engine/src/runtime/loader/migrate.cpp`; extend the version
   history above.
4. Update the cross-field rules in both languages if the member takes part in one (`validate.py`,
   `checks.cpp`), with the same paths and codes.
5. Regenerate the fixtures (`uv run python compiler/tests/data/b1/gen_fixtures.py`) and the examples
   (see below) so that `all-fields.json` has a non-default value for the new member, then run
   `uv run pytest compiler/tests` and `ctest -R "^B1"`. The C++ test `B1-T1 all-fields.json matches
   the hand-written expected value of every member` lists members by hand in
   `engine/tests/loader/test_roundtrip.cpp`; add the new member there.

## Notes

- Load time of `generic-grand-88` (373 KB): C++ about 5 ms, writing about 7 ms (GCC 13, `-O3`,
  Release flags, 4-core container); Python about 79 ms to load (including `jsonschema`) and 18 ms to
  write. No baseline is stored (B1 touches no audio-path code).
- A `std::optional` member that is present but `null` in the file is a `type` error; null is never
  accepted for an absent optional member.
- Provisional readings, all the least restrictive reading of a header comment: `lengthX`/`lengthY`
  and `thickness` are "at least 0" in the member table and strictly positive only for the `PlateModel`
  source; `strikeRatio` and `xRatio` are in [0, 1]; the Poisson ratios and moisture slopes are unbounded;
  `name` strings are not restricted (instrument names must contain no trademarks, which a loader cannot
  check).
